# ロードマップ: 計算の核から始めて、kamoku につなぐ

終点は、勤怠の集計から給与の仕訳を作り、会計ソフト kamoku に渡すところです。各段階は、それだけで使える形で終わらせます。次の段階が遅れても、前の段階が無駄にならないようにするためです。

| 段階 | 中身 | 終わりの基準 | 状態 |
|---|---|---|---|
| Phase 0 | 計算の部品（時間の区分、36協定、年次有給休暇）とコマンドライン | 差分試験・変異試験・公的な数値例がすべて通る。権利の確認記録が揃う | 完了・公開済み（2026-10-15）。社労士の確認が残る |
| Phase 1 | 保存（SQLite、追記だけ）、手元のサーバー、打刻と承認の画面 | 架空の10人で、打刻から月次の締めまでを通せる。画面の採点に合格する | 未着手 |
| Phase 2 | 割増賃金の金額、給与仕訳の書き出し、変形労働時間制とフレックス | kamoku が読める形で、1か月分の給与仕訳を渡せる | 未着手 |
| Phase 3 | 社内チャットとの連携（打刻・申請・承認・月次の通知） | チャットの発言だけで、打刻から承認まで通せる | 未着手 |
| Phase 4 | 複数の道具を束ねる共通部分（人の台帳、監査の記録、導入手順） | 勤怠と会計を、1つの手順で導入できる | 構想のみ |

## Phase 0: 計算の部品

`kintai-core`（日付・分・区間）、`kintai-jp-labor`（法令の表と規則）、`kintai-import`（打刻CSVの取込）、`kintai-cli`（`report` `check` `leave` `explain` `retention` `case` `demo`）を作ります。仕様は `docs/spec/` の受け入れ条件に書き、試験はそれを参照します。計算の正しさは、公的な数値例、別実装（Python）との差分試験、変異試験の3つで確かめます。

## Phase 1: 保存・サーバー・画面

その前段として、Phase 0の計算結果を読む[月次確認画面](review.md)と[読み取り専用MCP](mcp.md)を追加しました。保存や打刻の実装とは区別します。

打刻、修正の申請と承認、月次の締め、出勤簿と賃金台帳向けの書き出し、36協定のアラート、年次有給休暇管理簿を、手元のサーバーとブラウザで動かします。記録は追記だけにして、修正は理由つきで足します。複数の利用者がいるので、kamoku と違い、認証と役割（従業員・承認者・管理者）が要ります。実装の前に、ユーザーストーリーと画面のUXを書きます。

## Phase 2: kamoku への接続

勤怠の集計に、基礎賃金を与えて金額を出します。端数処理は、通達が認める方法を選べるようにします。給与の仕訳（給料賃金、預り金、未払費用など）は、kamoku が読める取込の形式で書き出します。接続は、ファイルを渡す形から始めます。2つのデータベースを共有しません。形式は[スイートの構想](suite.md)にあります。

## Phase 3: 社内チャットとの連携

チャットそのものは作りません。既存のチャット（Zulip、Mattermost、Slack）に、コマンドと通知で接続する小さな部品を作ります。理由は[スイートの構想](suite.md)に書きました。

## やらないと決めたこと

| やらないこと | 理由 | 見直す条件 |
|---|---|---|
| 顔認証・位置情報による打刻 | 個人情報の扱いが重く、特許の確認もできていない | 弁理士と社会保険労務士の確認が得られたとき |
| 36協定届の作成と電子申請 | 社会保険労務士法の業務範囲に近く、保守者1人では責任を持てない | 社会保険労務士の協力者が現れたとき |
| 他社の勤怠サービス形式の取込・書き出し | 規約が競合する開発を禁じていることがあり、契約者として実機で確かめられない | 規約の確認と法的な見解が得られたとき |
| 労働者ごとの判断の自動化（休憩の自動控除など） | 黙って控除すると、法令違反を見えなくする | 設定として明示し、画面に出す設計ができたとき |
