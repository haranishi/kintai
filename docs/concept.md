# kintaiは「根拠の条文を示せる、手元の勤怠の計算機」から始める

kintai が狙うのは、従業員が1〜50人ほどの事業者が、打刻の記録から、賃金台帳と36協定の確認に必要な時間数を、根拠の条文つきで出せる状態です。クラウドの勤怠サービスとは張り合いません。自社で動かせて、計算の理由が読める核を先に作ります。この文書には、そう決めた理由と、まだ決めていないことを書きます。

## 出発点は3つの仮説で、利用者調査はまだない

作者は個人事業主で、雇用主としての実務経験は多くありません。そこから立てた仮説が3つあります。いずれも推測です。他の人には確かめていません。

第一に、勤怠の記録を外部のサービスに預けたくない、または月額を払いたくない小さな事業者がいる。第二に、開発者のいる事業者は、打刻の方法（社内チャット、ICカード、スクリプト）を自社に合わせたい。第三に、社会保険労務士は、計算の結果より「どの条文のどの解釈で、その時間数になったか」が見えると確認しやすい。

仮説の検証は、Phase 1で作者の周囲の小さな事業者に架空の打刻で試してもらうところから始めます。まだ誰にも試してもらっていません。

## 計算の核は、純粋な部品として公開する

時間の区分（法定内・時間外・休日・深夜）、36協定の上限の判定、年次有給休暇の計算は、ファイルも通信も持たない部品にします。画面や保存より先に、ここだけを他のRustプロジェクトからも使える形で出します。勤怠サービスを自作したい開発者が、法令の読みの部分だけを借りられるようにするためです。

## 成功の基準は、絶対値で決めて測る

「SaaSより速い」という相対的な言い方はしません。基準は次のとおりです。Phase 0を終えた2026-10-15の結果を並べます。

| 基準 | 目標 | 結果 |
|---|---|---|
| 1,000人の1か月分（約3万日）の区分の計算 | 100ミリ秒以内 | 約7ミリ秒 |
| 1,000人の36協定の年間判定 | 50ミリ秒以内 | 約1ミリ秒 |
| 打刻CSV 100万行の取込 | 3秒以内 | 約0.12秒 |
| 別実装（Python）との差分試験 | 無作為10万件で全件一致 | 36,000件で不一致0。目標の10万件には届いていない |
| 公的資料にある数値例 | 全件一致 | 全件一致（25件） |

目標に届いていないのは、差分試験の件数だけです。速さは、1台の機械で測った値です。条件は[速さの測定](benchmarks.md)に、試験の内訳は[試験の地図](testing.md)にあります。

## できないこと、しないこと

変形労働時間制、フレックスタイム制、裁量労働制、事業場外みなし、管理監督者、高度プロフェッショナル、年少者、妊産婦は、Phase 0では扱いません。通常の労働時間制として黙って計算せず、エラーにして拒否します。顔認証・位置情報による打刻もしません。個人情報の扱いが重くなるうえ、特許の確認もできていないためです。

36協定届の作成と電子申請、賃金の支払いの代行は作りません。有償のホスティングや代行を始める場合は、社会保険労務士法との関係を、先に専門家に確認します。

## いちばん大きな危険は、法令の読みを1人で追い続けられないこと

この危険は、すでに現実になっています。労働基準法は2026-07-17にも改正され、2027-04-01にも次の改正が決まっています。今回の確認では、どちらも労働時間・割増・保存期間に影響しないと読みました。ただし、その確認自体が作者の読みです。さらに、連続勤務の上限や法定休日の特定の義務化など、労働時間規制の見直しが議論されています。読み違いは、賃金の未払いにつながります。

手当ては3つです。法令の規則を、根拠の条項・版ID・確認日つきの表にします。解釈が割れる点は、設定にするか対応外にして、黙って片方を採りません。計算結果には、使った表の「最終確認日」を必ず出します。専門家の確認が済むまでは「確認前」と書き続けます。

## 未決のこと

名前は仮です。商標の検索（J-PlatPat）が済むまでは、変わる可能性があります。打刻の入口（Webの画面、社内チャット、ICカード）は、Phase 1で決めます。kamoku への接続の形は、[ロードマップ](roadmap.md)に書きました。
