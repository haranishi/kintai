# 試験の地図: 何を、どの層で、どうやって確かめているか

kintai の試験は8つの層に分かれています。下の層ほど速く、失敗の場所を絞りやすい。上の層ほど本物に近く、部品の組み合わせまで確かめます。PRの前は `cargo xtask check-all` を流してください。下表の件数はPhase 0完了時のもので、画面・MCP・要件データの追加試験は後半に説明します。

## 層ごとの役割

| 層 | 確かめること | 流し方 | 件数 |
|---|---|---|---:|
| 暦と区間（core） | 日付の曜日・加減・月の期間を、`chrono` と全日付（2000〜2099年、型の範囲は1900〜2200年）で突き合わせる。打刻の対 | `cargo test -p kintai-core` | 63 |
| 計算の規則（jp-labor） | 区分、60時間超、曖昧さ、対応外の表、36協定、年休、祝日、休憩、月次、説明。性質の試験（proptest）つき | `cargo test -p kintai-jp-labor` | 187 |
| 取込（import） | CSVの文字コード、BOM、見出し、入力の上限、行番号。壊れたバイト列でもパニックしない | `cargo test -p kintai-import` | 28 |
| コマンド（cli） | 実際のバイナリを動かし、出力の形、終了コード、壊れた入力、エラー文に入力の中身が出ないこと、権限 | `cargo test -p kintai-cli` | 160 |

| 別実装の照合 | Pythonが、仕様だけから、1分ずつ数えて書いた別実装。同じ入力で、終了コードと出力を比べる | `python3 tools/oracle/selftest.py`、`python3 tools/difftest.py --cases 2000 --seed 1` | 数値例25、無作為36,000 |

## 試験が「門番」になっているか

試験が通っていても、守りたい規則を守っているとは限りません。そこで、次の4つで試験の側を確かめます。

**別実装との差分試験**は、無作為のケース（区分、36協定、年休）を、本体とPythonの別実装の両方に通して比べます。別実装は本体のコードを見ずに書かれているので、仕様の読み違いや境界の取り違えが、食い違いとして出ます。種を6つ（1・2・3・7・42・99）、種類ごとに2000件、合計36,000件で、不一致は0件でした。比べたのは、終了コード、出力のJSON、エラーのコードです。この過程で、仕様の誤りを4件見つけ、直しました（日付の範囲、導出例の誤り、うるう年の期間の終わり）。

**変異試験**は、ソースの1か所を壊して試験を流し、赤くなれば「検出」、ならなければ「生き残り」と数えます。生き残りは試験の穴です。323件の変異は、4800×n、2700、6000、翌月1日の規則、失効の当日、半日、30分丸め、休憩の360・480分、入力の上限など、壊れると結果が狂う境界を選んであります。最終は生き残り0件です。1回目に生き残った誤りは十数件あり、どれも「その値を含む側」の境界だったので、試験を足しました。重い全件の試験は週次CIで流します。PRでは画面・MCP・仕様対応の8件を流します。

**独立した査読**は、書いた担当とは別のセッションが行いました。仕様の法令の根拠を一次資料で照合した査読（🔴1件、🟡11件を仕様に反映）、権利・規制の文書の事実を一次資料で照合した査読（81か所、誤り2件を直した）、実装の読み取りレビュー（誤った結果とパニックは見つからず、🟡8件を直した。仕様から書いたモデルとの突き合わせ約5,300人分と、壊した入力5,000回を含む。記録は `.agent-harness/runs/2026-10-15-phase0/review-l2.md`）です。

**公的な数値例**は、厚生労働省などの資料の例を、期待値つきで `docs/spec/vectors/` に置いています。出典が公的な例と、そこから導いた例（`derived-`）は区別してあります。

## 仕様との対応

仕様の約束は `docs/spec/` の受け入れ条件（`AC-02.1` など）に書いてあります。127件の条件のうち、人が確かめる3件を除くすべてに、対応する試験や測定用プログラムからの参照があります。`cargo xtask check-spec-trace --strict` が、参照の無い条件で失敗します。Rustは試験・測定用の例・単体試験モジュール、Pythonはtools、ブラウザはweb-testsの参照を数えます。実装のコメントだけでは条件を満たせません。参照は対応の目印で、試験の実行結果やカバレッジとは別です。

## CIで流れるもの

PRごとに、次のジョブが流れます（`.github/workflows/ci.yml`）。公開した2026-10-15の初回の実行では、文書のリンク検査だけが失敗しました（公開しないファイルへのリンクが残っていた）。直して、全ジョブが通っています。

- 試験（Linux・macOS・Windows）: 書式、clippy、全試験、文書の警告
- 最小のRustバージョン（1.88）、依存のライセンスと脆弱性（cargo deny）、ライセンス表示（REUSE）
- 文書のリンクと行数、仕様と試験の対応
- 別実装の照合（数値例と、種1・42・99のそれぞれ無作為1000件ずつ）
- 秘密情報の走査（gitleaks）

## 自動では確かめていないこと

追加した試験は、HTMLファイル・MCPの実プロセス、[公開要件の合成データ8件](spec/decision-regressions.md)、ブラウザの操作です。`npm run test:browser` も実行します（[手順](review.md)）。PRでは画面とMCPの変異5件・仕様対応の変異3件が検出されることを確認します。毎週月曜03:00 JSTには、全11ファイル331件の変異と、追加の種による差分試験を実行します。週次試験は手動でも起動できます（`.github/workflows/deep-tests.yml`）。

次は、人が確かめる必要があります。確かめた結果は、Issueに残してください。

- **法令の読みそのもの。** 試験は、仕様どおりに計算することを確かめます。仕様の側は、社会保険労務士の確認を受けていません（[確認してほしい点](legal/professional-review.md)）。別実装と本体が一致しても、読みが同じ誤りなら両方が誤ります。
- **Windowsでの画面操作。** WindowsのRust試験はCIに追加しました。ブラウザの自動試験はLinuxのChromiumです。
- **2051〜2099年の春分・秋分。** 公的な表がなく、近似式が2050年までの国立天文台の予想表と一致することだけを確かめました（[着手しやすい課題](good-first-issues.md)の5）。
- **実データでの使い心地。** 試験の入力はすべて合成です。人が読む出力の読みやすさは、利用者に見てもらっていません。
- **測定の別環境。** 速さは1台の機械で測りました。

## 試験を足すとき

- 条件を満たす試験なら、名前かコメントに `AC-xx.y` を書く。
- 守りを足したら、その守りを外す誤りを `tools/mutations/*.json` に足して、赤くなることを確かめる（`cargo xtask mutate`）。
- 仕様を変えるときは、先に仕様を直す。別実装も仕様から直し、本体のコードを見ながら直さない。
- 合成データだけを使う。実在の従業員・会社の名前は入れない。
