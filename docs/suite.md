# 構想: 日本の小さな事業者の事務を、手元で動くOSSの組み合わせで完結させる

目標は、従業員が1〜30人ほどの事業者が、勤怠・給与・記帳・社内連絡を、自社で動かせるOSSだけで回せる状態です。まだ構想で、約束ではありません。保守者は1人なので、各部品は単体で役に立つ形で終わらせ、つなぐのはその後にします。

## 部品と状態

| 部品 | 役割 | 状態 |
|---|---|---|
| kamoku | 記帳と帳票（個人事業主向けの会計） | 公開済み（アルファ） |
| kintai | 勤怠の記録、法令に沿った時間の区分、36協定、年次有給休暇 | Phase 0 作業中 |
| 給与の計算 | 割増賃金の金額、社会保険料、源泉所得税、仕訳 | 構想（近い試作が既にあり、協業か取り込みを先に検討） |
| 社内連絡との接続 | 打刻・申請・承認・通知を、既存のチャットから行う | 構想 |

## つなぎ方の方針

**データベースを共有しない。** 部品どうしは、版つきのファイルの約束（JSON、CSV）で渡します。片方の保存形式を変えても、もう片方が壊れないようにするためです。最初に決める約束は2つです。

- `attendance-summary.v1`: 従業員・期間ごとの区分別の分、日数、休暇、使った表の確認日。
- `journal.v1`: 日付、摘要、明細（科目コード、借方か貸方か、金額、メモ）、再送防止の印。kamoku の `POST /entries` の `journal` 形式（貸借が合わなければ拒否する）に1対1で対応させる。給与なら、給料賃金を借方、預り金と未払金を貸方にする。科目コードの対応は設定にする。ファイルを取り込む入口は、kamoku 側に別に足す（相談事項）。

**人の台帳は、最小にする。** 従業員の識別子、氏名、入社日、雇用の区分だけを共通にします。給与の額や評価など、他の部品に要らない情報は渡しません。個人情報なので、部品ごとに保護の責任が増えるためです。

**追記だけの記録を、共通の作法にする。** 訂正は理由つきで足し、ハッシュで連ねます（kamoku と同じ考え方）。改ざんを防ぐのではなく、見つけます。

## チャットは作らず、つなぐ

Slack風のチャットを自作する案は、見送りました。既存のOSSが大きく（Rocket.Chat、Mattermost、Zulip は各2.6万〜4.6万スター）、2026年に作られた「Slack代替」は最大でも70スター程度でした（2026-10-15、GitHub）。作っても、勤怠や会計の機能より先に、チャットの保守が重くなります。

代わりに、既存のチャットから `打刻` `休暇申請` `承認` を行い、月次の締めを通知する小さな接続部品を作ります。対象はまず Zulip（Apache-2.0）と Slack です。接続は外向きの通知と受け口だけにして、チャットの内部には依存しません。

自作を再検討する条件は3つです。接続部品の利用者がいること。保守を分担できる人がいること。既存のチャットでは満たせない要件が具体的に出たこと。

## 順序

kamoku の画面の仕上げ、kintai の Phase 0 と Phase 1 を先に終えます。接続は、各部品が単体で使われた後に始めます。順序の理由は、単体で価値がない部品を束ねると、保守の負担だけが増えるためです。段階は[ロードマップ](roadmap.md)にあります。

## 危険

保守者が1人で、法令の追従が各部品に要ります。追従は、表の更新だけでは終わりません。改正のたびに、通達や解釈の読み直しが要ります。従業員の個人情報を複数の部品が扱うので、事故の影響が大きくなります。「全部入り」と見られると、各部品の未熟さが目立ちます。手当ては、単体での価値、データの最小化、確認前であることの明記、専門家の確認を得るまで「対応済み」と言わないことです。
